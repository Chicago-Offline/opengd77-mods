The power-off animation

OpenGD77 · MD-UV380 / RT3S

Stock OpenGD77 says POWER OFF and 73 and then the radio goes away. It is about a second and a half of screen time that nobody was using, so it now has a Thompson in it.

This one is a sibling of the boot screen mod — same problem, opposite end of the session. It also turned into a much better debugging story than I wanted at the time.

There is a frame clock already, and it is free

The splash screen has no animation loop, which is the whole reason the boot mod needed a timer callback. I assumed the power-off screen would be the same and started looking for somewhere to hang one.

It is not the same. The menu dispatcher calls the current screen's handleEvent() on every tick, whether or not anything actually happened: 

menuControlData.stack[menuControlData.currentItem].function(ev, false);

No ev->hasEvent gate. And ev->time is refreshed from ticksGetMillis() before each dispatch, so the screen is handed a live millisecond clock a few hundred times a second for free. Stash the time on isFirstRun, subtract, divide by the frame length: 

uint8_t frame = ((ev->time - tgAnimStartTime) / TG_FRAME_MS) % TG_FRAMES;

Redraw only when frame differs from the last one drawn. No timer, no callback, no re-arming, nothing to tear down when the screen exits.

What is actually drawn

The gun is 120×40, one bit, row-major and MSB-first with each scanline padded to whole bytes — 15 bytes a row, 40 rows, 600 bytes of flash. That is the layout displayDrawBitmap() expects, so it goes straight to the panel with no conversion step.

Twelve frames at 40 ms is a 480 ms loop. Recoil and muzzle flash are small lookup tables rather than logic: 

static const uint8_t tgRecoil[TG_FRAMES]    = { 4, 2, 1, 4, 2, 1, 4, 2, 1, 4, 2, 1 };
static const uint8_t tgFlashSize[TG_FRAMES] = { 2, 3, 1, 2, 3, 1, 2, 3, 1, 2, 3, 1 };

Four bursts per loop. The recoil value shifts the whole gun left by a few pixels on the firing frame and lets it walk back; the flash index picks one of three sprites pinned to the muzzle at TG_MUZZLE_X 119, TG_MUZZLE_Y 5. The largest is 23×25, the smallest 10×11, and cycling big-bigger-small is what keeps it from looking like a blinking lamp.

Brass is 48 pre-computed shell positions indexed per frame, so the casings arc out and tumble on a fixed path instead of being simulated. The entire mod is a little over 900 bytes of sprite data and no floating point.

Giving it time to be seen

Stock gives the power-off screen 500 ms, which is one loop and a bit — long enough to look like a glitch. That constant is now three clean loops: 

const uint32_t POWEROFF_DURATION_MILLISECONDS = 1440;

1440 is exactly 3 × 480, so the animation ends on a frame boundary rather than being cut mid-burst.

The stock screen's rounded rectangle and drop shadow are gone. At this size the frame was just a box drawn around a gun, and losing it gives the sprite the full panel width.

The boolean that cost an evening

The first build compiled clean, flashed clean, and showed the POWER OFF text on a blank screen. No gun, no flash, no brass.

I spent a while on the wrong suspects, and they were all plausible. Maybe the TG_ANIMATION_SUPPORTED guard was failing and the stock branch was compiled in. Maybe the preprocessor nesting was wrong and the drawing code sat in a dead #if. Maybe the sprite table was empty. Every one of those was checkable, and every one of them came back fine: the guard passes on a 160×128 panel, the #else branch is live, and the gun table has 245 non-zero bytes in it.

The actual answer was one line down in the display layer: 

screenBuf[i] = isInverted ? foregroundColour : backgroundColour;

displayDrawBitmap() passes its last argument straight through to displaySetPixel(), and I had been passing false. The parameter is called isInverted, so false reads like not inverted, draw it normally. What it means is paint the background colour.

So the gun was being drawn. Correctly, every frame, in exactly the colour of the screen behind it. The text was visible the whole time because the font renderer does not go through displaySetPixel() — which is precisely why the symptom pointed away from the real cause.

This is the second inverted boolean in the same display layer. The boot mod has the opposite problem: in displayConvertGD77ImageData() a set bit paints the background, so an intuitively packed image comes out as a negative. Two different inversions, two different functions, no consistent rule between them. Assume nothing about polarity here and check the implementation every time.

Six call sites were wrong — gun body, three muzzle flashes and the brass loop. Flipping them to true fixed all of it at once. The comment above the brass loop had confidently documented the wrong convention, so that went too.

Not on the DM1701

The animation is gated on panel size: 

#if (DISPLAY_SIZE_X >= 160) && (DISPLAY_SIZE_Y >= 128)

That looks like it covers every colour target, but the DM1701 and RT84 define DISPLAY_Y_OFFSET as 8, which makes DISPLAY_SIZE_Y 120 rather than 128. They fail the test and fall back to the stock POWER OFF / 73 screen, which is the intended outcome — a 120×40 sprite plus text does not fit in 120 rows. Worth knowing that the guard is doing real work rather than being decorative.

Get the patch

chioff-tommygun.patch — a plain unified diff against the OpenGD77 R20260131 release source. Two files, 256 lines added, seven removed, nothing binary. 

git apply --3way chioff-tommygun.patch

It touches uiPowerOff.c and adds chioff_tommygun.h. No settings, no menus, no language strings, nothing in the RF or codec paths. There is no toggle for it; it replaces the power-off screen outright on panels that qualify.

Want different artwork? tools/gen_tommygun.py generates the header — sprites, recoil table and shell paths. Edit, re-run, rebuild.

Where it stands

This one has run on hardware, which is the difference between this post and the boot screen one. Builds clean under STM32CubeIDE headless with GCC 14.3.1, zero errors, and the five warnings are the pre-existing AMBE absolute-branch ones that have nothing to do with this change.

The exact image that was flashed and confirmed is published as chioff-chicago-combined-R20260131.bin. It is not a tommygun-only build — it carries every mod on this site, including the boot animation, and it sets CHIOFF_BOOT_ANIM_OVERRIDES_IMAGE, which makes the skyline take precedence over a boot image stored in your codeplug. If you want this mod on its own, or you want to keep your stored boot image, build from the patch instead.
